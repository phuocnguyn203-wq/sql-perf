Phép JOIN

Join ghép lại những mảnh dữ liệu nằm rải rác, nên rất nhạy với độ trễ.
Index đúng vẫn là cách tốt nhất để join nhanh, nhưng index nào là đúng thì tùy thuật toán join.

Join ghép từng cặp table

Bài này đi theo chương 4 của cuốn SQL Performance Explained (Markus Winand, 2012); chữ "sách" trong bài là cuốn đó. Sách dùng Oracle; mỗi ví dụ ở đây được chạy lại trên PostgreSQL, và chỗ nào PostgreSQL làm khác, bài ghi rõ.

Phép join biến dữ liệu từ mô hình chuẩn hóa (normalized) sang dạng phi chuẩn hóa (denormalized), hợp với một mục đích xử lý cụ thể. Join đặc biệt nhạy với độ trễ khi seek đĩa, vì nó ghép những mảnh dữ liệu nằm rải rác. Index đúng lại là cách tốt nhất để giảm thời gian phản hồi. Nhưng index nào đúng thì phụ thuộc vào việc query dùng thuật toán nào trong ba thuật toán join phổ biến.

Có một điểm chung cho mọi thuật toán join: chúng chỉ xử lý hai table một lúc. Query SQL có nhiều table hơn phải chạy nhiều bước: trước hết join hai table thành một kết quả trung gian, rồi join kết quả đó với table tiếp theo, và cứ thế.

Thứ tự join không ảnh hưởng tới kết quả cuối, nhưng ảnh hưởng tới hiệu năng. Vì vậy optimizer xét mọi hoán vị thứ tự join và chọn cái tốt nhất. Nghĩa là riêng việc tối ưu một câu lệnh phức tạp cũng có thể thành vấn đề hiệu năng. Càng nhiều table, càng nhiều phương án plan phải xét: nói theo toán học là n! (tăng theo giai thừa). Điều này không thành vấn đề khi dùng bind parameter, vì plan đã dựng được tái dùng.

Quan trọng Câu lệnh càng phức tạp, dùng bind parameter càng quan trọng. Không dùng bind parameter giống như compile lại chương trình mỗi lần chạy.
Pipelining kết quả trung gian Kết quả trung gian giải thích thuật toán rất rõ, nhưng không có nghĩa database phải lưu nó lại (materialize), tức lưu cả kết quả của join thứ nhất rồi mới bắt đầu join tiếp theo. Database dùng pipelining để tiết kiệm bộ nhớ: mỗi row của kết quả trung gian được chuyển ngay sang phép join tiếp theo, không cần lưu cả tập kết quả.

Nested Loops

Thuật toán join cơ bản nhất: với mỗi row của query bên ngoài, chạy một query bên trong. Nhanh khi query bên ngoài trả về ít row.

N+1 selects: nested loops tự viết trong ứng dụng

Nested loops join hoạt động như hai query lồng nhau: query bên ngoài (outer, hay driving query) lấy kết quả từ một table, và với mỗi row của nó, một query thứ hai lấy dữ liệu tương ứng từ table kia.

Có thể tự cài thuật toán nested loops bằng "nested select". Nhưng làm vậy rất phiền, vì độ trễ mạng cộng thêm vào độ trễ đĩa, làm thời gian phản hồi còn tệ hơn. "Nested select" vẫn rất phổ biến, vì rất dễ viết ra mà không hề hay biết. Các công cụ ORM (object-relational mapping) đặc biệt "giúp" chuyện này, tới mức cái gọi là N+1 selects problem đã nổi tiếng một cách đáng buồn.

Ví dụ của chương này dùng table employees quen thuộc từ chương 2 (100.000 nhân viên, primary key (employee_id, subsidiary_id)) và thêm một table mới, sales: mỗi row là một lần bán hàng, ghi nhân viên nào bán, ngày nào, bao nhiêu tiền.

CREATE TABLE sales (
  sale_id       integer       PRIMARY KEY,
  employee_id   integer       NOT NULL,
  subsidiary_id integer       NOT NULL,
  sale_date     date          NOT NULL,
  eur_value     numeric(17,2) NOT NULL
);

Cặp (subsidiary_id, employee_id) trong sales trỏ tới nhân viên đã bán, tức primary key của employees. Table ở đây có 1.000.000 lần bán, chia ngẫu nhiên cho các nhân viên.

Ví dụ của sách: tìm các nhân viên có họ bắt đầu bằng 'WIN' và lấy mọi lần bán hàng của họ. ORM không sinh ra câu SQL join. Nó chạy một query lấy nhân viên, rồi với mỗi nhân viên tìm được, chạy một query lấy các lần bán của người đó. Bỏ bớt danh sách column, các câu SQL nó gửi tới database là:

-- 1 lần: tìm nhân viên
SELECT … FROM employees WHERE UPPER(last_name) LIKE 'WIN%';

-- N lần, mỗi nhân viên tìm được một lần: lấy sales của người đó
SELECT … FROM sales WHERE subsidiary_id = ? AND employee_id = ?;

Nếu câu thứ nhất (driving query) trả về N row, tổng cộng có N+1 câu select. Trên dữ liệu ở đây có 8 nhân viên như vậy:

Code ORM sinh ra N+1 select (Java, Perl, PHP, theo sách)

Java, JPA với CriteriaBuilder:

CriteriaBuilder queryBuilder = em.getCriteriaBuilder();
CriteriaQuery<Employees>
   query = queryBuilder.createQuery(Employees.class);
Root<Employees> r = query.from(Employees.class);
query.where(
  queryBuilder.like(
    queryBuilder.upper(r.get(Employees_.lastName)),
    "WIN%"
  )
);
List<Employees> emp = em.createQuery(query).getResultList();
for (Employees e: emp) {
  // process Employee
  for (Sales s: e.getSales()) {
    // process sale for Employee
  }
}

Hibernate JPA 3.6.0 sinh ra N+1 query:

select employees0_.subsidiary_id as subsidiary1_0_
       -- MORE COLUMNS
  from employees employees0_
 where upper(employees0_.last_name) like ?
  select sales0_.subsidiary_id as subsidiary4_0_1_
         -- MORE COLUMNS
    from sales sales0_
   where sales0_.subsidiary_id=?
     and sales0_.employee_id=?
  select sales0_.subsidiary_id as subsidiary4_0_1_
         -- MORE COLUMNS
    from sales sales0_
   where sales0_.subsidiary_id=?
     and sales0_.employee_id=?

Perl, DBIx::Class:

my @employees =
   $schema->resultset('Employees')
          ->search({'UPPER(last_name)' => {-like=>'WIN%'}});
foreach my $employee (@employees) {
    process Employee
   foreach my $sale ($employee->sales) {
       process Sale for Employee
   }
}

PHP, Doctrine query builder:

$qb = $em->createQueryBuilder();
$qb->select('e')
   ->from('Employees', 'e')
   ->where("upper(e.last_name) like :last_name")
   ->setParameter('last_name', 'WIN%');
$r = $qb->getQuery()->getResult();
foreach ($r as $row) {
   // process Employee
   foreach ($row->getSales() as $sale) {
      // process Sale for Employee
   }
}

DBIx::Class 0.08192 và Doctrine 2.0.5 sinh ra cùng một kiểu N+1 query như Hibernate.

Bật SQL logging Trong lúc phát triển, bật SQL logging và đọc lại các câu SQL được sinh ra. DBIx::Class: export DBIC_TRACE=1. Hibernate: <property name="show_sql">true</property>. Với JPA thì tùy provider, ví dụ hibernate.show_sql, eclipselink.logging.level, openjpa.Log. Doctrine chỉ bật được trong code (EchoSqlLogger); nhớ tắt khi lên production. Phần lớn ORM cho bật logging bằng code, nhưng như vậy dễ lỡ tay để nguyên thiết lập đó trên production.

Database làm y như ORM, nhưng trong một lần đi về

Dù "nested select" là anti-pattern, nó giải thích nested loops join rất rõ: database chạy join đúng như các ORM ở trên. Nó chạy query bên ngoài để lấy nhân viên, rồi với mỗi nhân viên tìm các lần bán của người đó. Vậy câu hỏi "join này cần index nào" quy về câu hỏi "hai câu select của ORM cần index nào". Xét lần lượt hai câu SQL ở trên.

Câu thứ nhất tìm nhân viên theo họ:

SELECT … FROM employees WHERE UPPER(last_name) LIKE 'WIN%';

Lúc này employees chỉ có index của primary key (employee_id, subsidiary_id). Index đó không giúp tìm theo tên, nên database phải scan cả 100.000 row. Index trên last_name cũng không giúp, vì điều kiện không tìm theo last_name mà theo UPPER(last_name) (chương 2, mục Functions). Cần một function-based index trên đúng biểu thức đó:

CREATE INDEX emp_up_name ON employees (UPPER(last_name));

Trên PostgreSQL ở đây, index này phải tạo kèm text_pattern_ops, vì với collation của database này LIKE chỉ dùng được index như vậy (chương 2, mục LIKE).

Câu thứ hai chạy một lần cho mỗi nhân viên tìm được, để lấy các lần bán của người đó:

SELECT … FROM sales WHERE subsidiary_id = ? AND employee_id = ?;

Hai điều kiện này chính là join predicate: điều kiện nối mỗi lần bán với nhân viên của nó. sales chỉ có index của primary key sale_id, không giúp gì cho hai column này. Không có index thì mỗi lần chạy là một full table scan sales, 1.000.000 row, và với 8 nhân viên là 8 lần đọc cả table. Cả hai điều kiện đều là toán tử bằng, nên một concatenated index trên hai column đó dẫn thẳng tới các lần bán của một nhân viên (chương 2, mục Concatenated Indexes):

CREATE INDEX sales_emp ON sales (subsidiary_id, employee_id);

Có index này, tìm các lần bán của Markus Winand (subsidiary 30, nhân viên 123) chỉ đọc 4 block để ra 7 lần bán.

Join trong SQL vẫn hiệu quả hơn nested select, dù nó tra index y như vậy, vì nó tránh được rất nhiều lần giao tiếp qua mạng. Nó còn nhanh hơn cả khi tổng lượng dữ liệu truyền đi nhiều hơn, vì thông tin nhân viên lặp lại ở mỗi lần bán. Đó là do hai chiều của hiệu năng ở chương 3: thời gian phản hồi và throughput. Trong mạng máy tính, hai chiều đó gọi là latency (độ trễ) và bandwidth (băng thông). Bandwidth ảnh hưởng ít tới thời gian phản hồi, còn latency ảnh hưởng rất nhiều. Nghĩa là với thời gian phản hồi, số lần đi về giữa ứng dụng và database quan trọng hơn lượng dữ liệu truyền đi.

Mẹo Chạy join trong database.

Phần lớn ORM có cách sinh ra SQL join. Quan trọng nhất có lẽ là chế độ eager fetching, thường cấu hình ở mức property trong entity mapping, ví dụ property employees trong class Sales. ORM sẽ luôn join table employees mỗi khi đọc table sales. Cấu hình eager fetching trong mapping chỉ hợp lý khi lúc nào cũng cần thông tin nhân viên kèm dữ liệu bán hàng.

Eager fetching phản tác dụng khi không phải lần nào đọc object cha cũng cần các record con. Với ứng dụng danh bạ, nạp cả sales khi hiện thông tin nhân viên là vô nghĩa. Có lúc cần dữ liệu bán hàng, nhưng không phải lúc nào cũng cần. Cấu hình tĩnh không phải giải pháp. Muốn hiệu năng tốt nhất, phải nắm toàn quyền quyết định join lúc chạy.

Điều khiển join lúc chạy trong ORM (Java, Perl, PHP, theo sách)

Java, JPA: Root<>.fetch() chỉ định khi nào và join thế nào. Ví dụ dùng left join để lấy cả nhân viên chưa có lần bán nào.

CriteriaBuilder qb = em.getCriteriaBuilder();
CriteriaQuery<Employees> q = qb.createQuery(Employees.class);
Root<Employees> r = q.from(Employees.class);
q.where(queryBuilder.like(
    queryBuilder.upper(r.get(Employees_.lastName)),
    "WIN%")
);
r.fetch("sales", JoinType.LEFT);
// needed to avoid duplication of Employee records
query.distinct(true);
List<Employees> emp = em.createQuery(query).getResultList();

Cảnh báo của sách: JPA và Hibernate trả về nhân viên cho mỗi lần bán, nên người có 30 lần bán xuất hiện 30 lần. Đó là hành vi theo đặc tả (EJB 3.0, mục 4.4.5.3 "Fetch Joins"); phải tự lọc trùng hoặc dùng distinct(). Hibernate 3.6.0 sinh ra:

select distinct
       employees0_.subsidiary_id as subsidiary1_0_0_
     , employees0_.employee_id as employee2_0_0_
       -- MORE COLUMNS
     , sales1_.sale_id as sale1_0__
  from employees employees0_
  left outer join sales sales1_
          on employees0_.subsidiary_id=sales1_.subsidiary_id
         and employees0_.employee_id=sales1_.employee_id
 where upper(employees0_.last_name) like ?

Có left join như mong muốn, nhưng thêm cả distinct không cần thiết. Từ khóa này đáng lo, vì phần lớn database sẽ thật sự lọc trùng; chỉ vài database nhận ra primary key đã bảo đảm không trùng. API gốc của Hibernate giải quyết ở phía client bằng result set transformer:

Criteria c = session.createCriteria(Employees.class);
c.add(Restrictions.ilike("lastName", 'Win%'));
c.setFetchMode("sales", FetchMode.JOIN);
c.setResultTransformer(Criteria.DISTINCT_ROOT_ENTITY);
List<Employees> result = c.list();
select this_.subsidiary_id as subsidiary1_0_1_
     , this_.employee_id as employee2_0_1_
       -- MORE this_ columns on employees
     , sales2_.sale_id as sale1_3_
       -- MORE sales2_ columns on sales
  from employees this_
  left outer join sales sales2_
          on this_.subsidiary_id=sales2_.subsidiary_id
         and this_.employee_id=sales2_.employee_id
 where lower(this_.last_name) like ?

Câu SQL gọn, không có mệnh đề thừa. Để ý Hibernate dùng lower() cho tìm kiếm không phân biệt hoa thường: chi tiết quan trọng khi tạo function-based index.

Perl, DBIx::Class với prefetch:

my @employees =
   $schema->resultset('Employees')
          ->search({ 'UPPER(last_name)' => {-like => 'WIN%'}
                   , {prefetch => ['sales']}
                   });
SELECT me.employee_id, me.subsidiary_id, me.last_name
       -- MORE COLUMNS
  FROM employees me
  LEFT JOIN sales sales
         ON (sales.employee_id   = me.employee_id
        AND  sales.subsidiary_id = me.subsidiary_id)
 WHERE ( UPPER(last_name) LIKE ? )
 ORDER BY sales.employee_id, sales.subsidiary_id

Để ý mệnh đề order by: ứng dụng không hề yêu cầu. Database phải sắp xếp kết quả theo đó, và việc này có thể tốn thời gian.

PHP, Doctrine:

$qb = $em->createQueryBuilder();
$qb->select('e,s')
   ->from('Employees', 'e')
   ->leftJoin('e.sales', 's')
   ->where("upper(e.last_name) like :last_name")
   ->setParameter('last_name', 'WIN%');
$r = $qb->getQuery()->getResult();
SELECT e0_.employee_id AS employee_id0
       -- MORE COLUMNS
  FROM employees e0_
  LEFT JOIN sales s1_
         ON e0_.subsidiary_id = s1_.subsidiary_id
        AND e0_.employee_id = s1_.employee_id
 WHERE UPPER(e0_.last_name) LIKE ?

Plan: NESTED LOOPS, tra index cho từng nhân viên

Khi được bảo join (cách làm ở khối "Điều khiển join lúc chạy" ở trên), ORM gửi một câu LEFT JOIN duy nhất thay cho N+1 câu select. Câu do Doctrine sinh ra, bỏ bớt danh sách column:

SELECT …
  FROM employees e
  LEFT JOIN sales s
         ON e.subsidiary_id = s.subsidiary_id
        AND e.employee_id   = s.employee_id
 WHERE UPPER(e.last_name) LIKE 'WIN%';

LEFT JOIN giữ cả những nhân viên chưa có lần bán nào. Plan Oracle của câu này, in trong sách, có thao tác NESTED LOOPS OUTER:

Cùng một hình dạng: Nested Loop với hai Index Scan. Index Scan trên sales_emp chạy 8 lần, mỗi nhân viên một lần, và tổng cộng ra 73 lần bán. Cả query đọc 43 block, trung vị 0,055 ms. Mẹo Hiểu ORM của mình và nắm quyền điều khiển join.

Nested loops join cho hiệu năng tốt nếu driving query trả về ít row. Ngược lại, optimizer có thể chọn một thuật toán join khác hẳn, như hash join ở mục sau. Nhưng chỉ khi ứng dụng dùng join để nói với database nó thật sự cần dữ liệu gì.

Hash Join

Thay vì tra B-tree cho từng row, nạp một phía của join vào bảng băm trong bộ nhớ một lần. Index trên các column join không giúp gì; index cho điều kiện chỉ lọc một table thì có.

Bảng băm thay cho những lần duyệt B-tree

Nested loops join nhanh khi query bên ngoài trả về ít row, như 8 nhân viên ở mục trước: 8 lần duyệt B-tree là không đáng kể. Nhưng mỗi row bên ngoài vẫn kéo theo một lần duyệt B-tree. Nếu query bên ngoài trả về hàng chục nghìn row, sẽ có hàng chục nghìn lần duyệt tree. Đó là điểm yếu mà hash join nhắm vào.

Ví dụ của sách cho mục này: lấy mọi lần bán trong sáu tháng gần nhất, kèm thông tin của nhân viên đã bán.

SELECT *
  FROM sales s
  JOIN employees e ON (s.subsidiary_id = e.subsidiary_id
                  AND  s.employee_id   = e.employee_id  )
 WHERE s.sale_date > DATE '2024-12-31' - INTERVAL '6' MONTH;

Sách tính sáu tháng tính từ ngày hôm nay. Ở đây mốc được cố định là ngày 31/12/2024, ngày cuối cùng có dữ liệu, để kết quả không đổi theo ngày chạy. Table sales chứa 1.000.000 lần bán của 10 năm, 2015–2024. Sáu tháng cuối có 50.650 lần bán, gần bằng con số trong ví dụ của sách (49.244).

Với nested loops, query này sẽ duyệt B-tree của employees khoảng năm mươi nghìn lần, mỗi lần bán một lần. Hash join làm khác: nó đọc một table một lượt và nạp các row vào một hash table (bảng băm) trong bộ nhớ, rồi đọc table kia và với mỗi row, dò bảng băm để tìm row tương ứng. Dò bảng băm trong bộ nhớ nhanh hơn nhiều so với duyệt một B-tree.

Muốn biết index nào giúp được hash join, hãy nhìn lại query. Nó có hai loại điều kiện:

  • Join predicate: s.subsidiary_id = e.subsidiary_id AND s.employee_id = e.employee_id. Điều kiện này nối hai table với nhau, nên chỉ kiểm tra được khi đã có row của cả hai table. Trong hash join, việc kiểm tra nó do bảng băm làm: key của bảng băm chính là các column join.
  • Điều kiện độc lập (independent predicate): s.sale_date > …. Điều kiện này chỉ nhắc tới một table, sales, nên kiểm tra được ngay lúc đọc từng row của sales, không cần biết gì về employees.

Vì bảng băm đã lo phần join predicate, index trên các column join không còn việc gì để làm. Index chỉ giúp được lúc đọc từng table: nó giúp đọc ít row hơn, nếu có một điều kiện độc lập để lọc.

Mẹo Index các điều kiện độc lập trong WHERE để cải thiện hiệu năng hash join.

Plan Oracle của query trên, in trong sách:

| Id | Operation          | Name      | Rows  | Bytes | Cost |
|  0 | SELECT STATEMENT   |           | 49244 |    59M| 12049|
|* 1 |  HASH JOIN         |           | 49244 |    59M| 12049|
|  2 |   TABLE ACCESS FULL| EMPLOYEES | 10000 |     9M|   478|
|* 3 |   TABLE ACCESS FULL| SALES     | 49244 |    10M| 10521|

Predicate Information (identified by operation id):
   1 - access("S"."SUBSIDIARY_ID"="E"."SUBSIDIARY_ID"

Bước đầu là full table scan nạp mọi nhân viên vào bảng băm (id 2). Bảng băm dùng join predicate làm key. Bước sau, database full table scan sales và bỏ mọi lần bán không thỏa điều kiện sale_date (id 3). Với các record còn lại, database tra bảng băm để lấy thông tin nhân viên. PostgreSQL chạy cùng plan đó:

PostgreSQL ghi bước dựng bảng băm thành node riêng, Hash, nằm dưới Hash Join. Mục đích duy nhất của bảng băm là làm cấu trúc tạm trong bộ nhớ để khỏi phải vào table employees nhiều lần. Bảng băm được nạp một lượt, nên không cần index để lấy từng record. Plan cũng không lọc gì trên employees, vì query không có điều kiện nào chỉ nhắc tới employees. Các index có sẵn trên join predicate, primary key của employees và sales_emp, không được dùng.

Quan trọng Index join predicate không cải thiện hiệu năng hash join.

Index cho điều kiện độc lập

Vậy index nào giúp được query này? Câu trả lời nằm ở điều kiện độc lập duy nhất của nó, điều kiện trên sale_date. Plan ở trên cho thấy vì sao: không có index, database đọc cả 1.000.000 row của sales rồi bỏ 949.350 row không thuộc sáu tháng gần nhất. Điều kiện này chỉ nhắc tới sales, nên một index trên sale_date dẫn thẳng tới đoạn sáu tháng đó, như mọi điều kiện khoảng ở chương 2, mà không cần đụng tới employees:

CREATE INDEX sales_date ON sales (sale_date);

Plan Oracle trong sách, sau khi có index này. sales được đọc qua index (dòng 3–4), còn employees vẫn full table scan, vì không có điều kiện nào lọc riêng table đó:

| Id | Operation                    | Name      | Bytes| Cost|
|  0 | SELECT STATEMENT             |           |   59M| 3252|
|* 1 |  HASH JOIN                   |           |   59M| 3252|
|  2 |   TABLE ACCESS FULL          | EMPLOYEES |    9M|  478|
|  3 |   TABLE ACCESS BY INDEX ROWID| SALES     |   10M| 1724|
|* 4 |    INDEX RANGE SCAN          | SALES_DATE|      |     |

Trong sách, cost của cả query (dòng 0 của hai plan Oracle) giảm từ 12.049 xuống 3.252. Trên máy này, thời gian giảm từ 144 ms xuống 95 ms. PostgreSQL đọc sales qua Bitmap Heap Scan: mỗi block chứa lần bán trong sáu tháng chỉ đọc một lần (chương 2, Slow Indexes). Vì lần bán của sáu tháng nằm rải khắp table, số block gần như không bớt (7.327 so với 7.379); phần nhanh hơn nhiều khả năng đến từ chỗ không phải kiểm tra điều kiện ngày trên cả 1.000.000 row.

Còn một khác biệt với nested loops. Ở nested loops, index cần có phụ thuộc thứ tự join: table bên trong (ở mục trước là sales) được tra một lần cho mỗi row bên ngoài, nên nó cần index trên các column join. Đảo thứ tự thì phải index table kia. Hash join thì đối xứng. Dù database dựng bảng băm từ employees hay từ sales, index sales_date vẫn làm đúng một việc: giúp đọc sales nhanh hơn.

Lưu ý Index cho hash join không phụ thuộc thứ tự join.

Bảng băm nhỏ hơn: chọn ít column hơn

Một cách hoàn toàn khác để cải thiện hash join là thu nhỏ bảng băm. Cách này hiệu quả vì hash join chỉ tối ưu khi cả bảng băm nằm vừa trong bộ nhớ. Optimizer vì vậy tự dùng phía nhỏ hơn của join làm bảng băm. Plan Oracle ghi lượng bộ nhớ ước tính ở cột "Bytes": ở plan trên, employees cần 9 MB, là phía nhỏ hơn.

Cũng có thể thu nhỏ bảng băm bằng cách sửa câu SQL, ví dụ thêm điều kiện để database nạp ít record ứng viên hơn vào bảng băm. Với ví dụ trên, đó là thêm một điều kiện trên thuộc tính department để chỉ xét nhân viên bán hàng. Cách này cải thiện hash join kể cả khi không có index trên department, vì database không phải lưu vào bảng băm những nhân viên không thể có lần bán nào. Khi làm vậy phải chắc chắn không có record sales nào của nhân viên thuộc phòng ban khác. Dùng constraint để bảo vệ giả định đó.

Khi thu nhỏ bảng băm, yếu tố quan trọng không phải số row mà là dung lượng bộ nhớ. Thực ra cũng có thể thu nhỏ bảng băm bằng cách chọn ít column hơn, chỉ những thuộc tính thật sự cần:

SELECT s.sale_date, s.eur_value
     , e.last_name, e.first_name
  FROM sales s
  JOIN employees e ON (s.subsidiary_id = e.subsidiary_id
                  AND  s.employee_id   = e.employee_id  )
 WHERE s.sale_date > DATE '2024-12-31' - INTERVAL '6' MONTH;

Cách này hiếm khi gây lỗi, vì bỏ nhầm column thường sẽ sớm báo lỗi. Trong sách, nó cắt bảng băm từ 9 MB xuống 234 KB, giảm 97%. Trong sách, mỗi nhân viên chiếm khoảng 900 byte trong bảng băm (9 MB cho 10.000 nhân viên), vì table của sách có những column lớn. Table employees ở đây không có column lớn như vậy, nên mỗi row trong bảng băm chỉ hẹp đi từ 43 xuống 25 byte. Chừng đó có đáng kể không? Phải xem bảng băm có vừa bộ nhớ hay không.

PostgreSQL không cho một thao tác dùng bao nhiêu bộ nhớ cũng được. Mỗi thao tác sắp xếp hay băm được cấp tối đa work_mem (mặc định 4MB); riêng bảng băm được gấp hash_mem_multiplier lần mức đó, ở đây là 8 MB. Bảng băm lớn hơn mức này thì PostgreSQL chia các row thành nhiều phần, gọi là batch: mỗi lúc chỉ giữ một batch trong bộ nhớ, các batch còn lại ghi tạm ra đĩa rồi đọc lại sau. Ghi và đọc lại đĩa tạm là phần việc thêm mà một bảng băm vừa bộ nhớ không phải làm. Với hai câu SQL ở đây:

Chọn ít column, thời gian giảm tiếp xuống 65 ms (biểu đồ ở trên).

Mẹo Chọn ít column hơn để cải thiện hiệu năng hash join.

Thoạt nhìn thì bỏ vài column khỏi câu SQL có vẻ đơn giản, nhưng với ORM đó là thách thức thật sự. Hỗ trợ cho cái gọi là partial object rất ít.

Chọn ít column trong ORM (Java, Perl, PHP, theo sách)

Java: JPA định nghĩa FetchType.LAZY trong annotation @Basic, áp dụng ở mức property:

@Column(name="junk")
@Basic(fetch=FetchType.LAZY)
private String junk;

Nhưng provider được phép bỏ qua nó (EJB 3.0 JPA, mục 9.1.18). Hibernate 3.6 cài lazy property fetching bằng bytecode instrumentation lúc compile. Cách này trong suốt với ứng dụng, nhưng mở ra một chiều mới của N+1: một câu select cho mỗi record và mỗi property. Nguy hiểm hơn nữa vì JPA không cho chọn eager fetching lúc chạy khi cần. HQL của Hibernate giải quyết bằng mệnh đề FETCH ALL PROPERTIES:

select s from Sales s FETCH ALL PROPERTIES
 inner join fetch s.employee e FETCH ALL PROPERTIES
 where s.saleDate >:dt

Một cách khác là dùng data transport object (DTO) thay cho entity, khởi tạo object ngay trong query (HQL và JPQL như nhau):

select new SalesHeadDTO(s.saleDate , s.eurValue
                       ,e.firstName, e.lastName)
  from Sales s
  join s.employee e
 where s.saleDate > :dt

Perl: DBIx::Class không đóng vai entity manager, nên kế thừa không gây vấn đề aliasing. Định nghĩa class Sales ở hai mức:

package UseTheIndexLuke::Schema::Result::SalesHead;
use base qw/DBIx::Class::Core/;
__PACKAGE__->table('sales');
__PACKAGE__->add_columns(qw/sale_id employee_id subsidiary_id
                            sale_date eur_value/);
__PACKAGE__->set_primary_key(qw/sale_id/);
__PACKAGE__->belongs_to('employee', 'Employees',
           {'foreign.employee_id'   => 'self.employee_id'
           ,'foreign.subsidiary_id' => 'self.subsidiary_id'});

package UseTheIndexLuke::Schema::Result::Sales;
use base qw/UseTheIndexLuke::Schema::Result::SalesHead/;
__PACKAGE__->table('sales');
__PACKAGE__->add_columns(qw/junk/);
my @sales =
   $schema->resultset('SalesHead')
          ->search($cond
                  ,{      join => 'employee'
                   ,'+columns' => ['employee.first_name'
                                  ,'employee.last_name']
                   }
                  );

Không chọn được column của table gốc (SalesHead): câu SQL lấy mọi column của sales và chỉ các thuộc tính được chọn của employees.

PHP: Doctrine 2 chọn thuộc tính lúc chạy bằng từ khóa partial, và phải chọn rõ các column primary key:

$qb = $em->createQueryBuilder();
$qb->select('partial s.{sale_id, sale_date, eur_value},'
          . 'partial e.{employee_id, subsidiary_id, '
                     . 'first_name , last_name}')
   ->from('Sales', 's')
   ->join('s.employee', 'e')
   ->where("s.sale_date > :dt")
   ->setParameter('dt', $dt, Type::DATETIME);

Object trả về tương thích với object đầy đủ, nhưng các column không chọn vẫn chưa khởi tạo, và truy cập chúng không báo lỗi.

Sort Merge

Ghép hai danh sách đã sắp xếp như kéo khóa. Đối xứng tuyệt đối, nhưng sắp xếp cả hai phía rất tốn kém, trừ khi index đã cho sẵn thứ tự.

Kéo khóa hai danh sách đã sắp xếp

Sort-merge join ghép hai danh sách đã sắp xếp như một chiếc khóa kéo. Cả hai phía của join phải được sắp theo join predicate.

Sort-merge join cần cùng loại index như hash join: index cho các điều kiện độc lập, để đọc mọi record ứng viên một lượt. Index join predicate là vô ích. Tới đây mọi thứ giống hash join. Nhưng sort-merge join có một điểm riêng: đối xứng tuyệt đối. Thứ tự join không tạo khác biệt gì, kể cả về hiệu năng. Tính chất này rất có ích cho outer join. Với các thuật toán khác, chiều của outer join (left hay right) quyết định thứ tự join; với sort-merge join thì không. Sort-merge join thậm chí làm được left và right outer join cùng lúc: cái gọi là full outer join.

Sort-merge join chạy rất tốt khi đầu vào đã sắp xếp, nhưng hiếm khi được dùng, vì sắp xếp cả hai phía rất tốn kém. Hash join chỉ phải xử lý trước một phía.

Sách không có ví dụ riêng cho mục này. Để xem PostgreSQL chạy sort-merge join thế nào, có thể tắt hash join cho phiên làm việc (SET enable_hashjoin = off, thay cho một hint) và chạy lại query chọn ít column ở trên:

Phía sales phải qua một bước Sort. Phía employees thì không: PostgreSQL đọc nó theo thứ tự của primary key (Index Scan trên employees_pkey), vốn đã sắp theo đúng các column join. Đó chính là điểm mạnh của sort-merge join đã nói ở trên: tận dụng thứ tự của index để khỏi phải sắp xếp. Cái giá là đọc employees từng row theo index, 106.587 lần đọc block. Kết quả: 84 ms, chậm hơn hash join chọn ít column (65 ms), nên khi được phép, PostgreSQL chọn hash join.

Chương 6, "Sorting and Grouping", giải thích kỹ cách dùng thứ tự của index để tránh hẳn bước sắp xếp. Dù vậy, trong nhiều trường hợp hash join vẫn tốt hơn.
